## 审查结论

项目已有严格 TypeScript 检查、较广的离线测试、有界 SSE 解析和背压、串行配置写入、凭据文件锁、代理索引与日志环形缓冲。应继续沿用这些实现，避免再次引入全量扫描或复制共享状态。当前主要问题是新增功能在不同入口重复接线，以及大处理器混合协议流程、流生命周期和基础策略。

## 模块与维护边界

- `auth`：凭据解析、选择、账户文件事务。套餐判定只返回请求局部结果，不能回写共享配置。
- `config`：默认值、YAML/环境变量校验和编辑。管理端、请求层应引用同一默认值来源。
- `proxy`：请求编排、传输、重试、验证码和响应构造。流处理单独拥有 reader、取消与完成回调。
- `responses`：历史条目转换与内存缓存；缓存的访问顺序与过期顺序独立维护。
- `translator`：协议对象与事件转换，不持有认证、磁盘和全局请求状态。
- `admin` / `server`：路由与界面边界；继续使用现有配置写队列、日志缓冲与安全门控。
- `Android-APP`：Kotlin 生命周期、进程管理与 UI。控制协议变更必须同步 TypeScript 与 Kotlin；本轮无需变更协议。

### 行为边界

- 缓存的 TTL 仍从写入时计算，`get()` 只更新 LRU；到截止时间本身仍有效，超过截止时间才过期。过期清理先于容量淘汰，支持写入期间时钟回拨。
- 缓存的截止时间和字节大小由缓存内部持有。返回历史仍是原对象；修改对象内容不会重新计量，修改 `createdAt` 也不会修改缓存期限。测试通过注入时钟验证过期，不再忙等或修改历史时间戳。
- 单个不可序列化历史不写入缓存，即使字节预算配置为无限大；数量与总字节预算继续生效。
- 规范化缓存标记保持引用和原请求格式；其他位置的标记仍删除，带额外字段的目标标记仍归一化。Responses 将已翻译对象传给会话解析，减少一次重复 JSON 解析。
- 验证码、加速卡、路由、领取、更新、CLI/TUI 和控制端宿主计时器统一使用已有隔离封装；验证码 guest 自己的窗口计时器保持原职责。
- Responses 失败、批量完成与流取消均会结束活动通知；不满足加速卡资格的请求仍不延长旧账号抽卡循环。加速卡回退重发前主动释放旧响应。

## 性能对比

同一机器、Node **v24.22.1**、同一脚本分别运行基线和工作树；每个场景预热一次，采样五次，取中位数。缓存场景保留相应数量的未过期条目，连续替换 10000 次。原始采样见 [performance-2026-10-26.json](performance-2026-10-26.json)。

| 场景 | 基线 | 优化后 |
| --- | ---: | ---: |
| 1000 条历史，10000 次写入 | 135.226 ms | 12.464 ms |
| 10000 条历史，10000 次写入 | 833.976 ms | 25.731 ms |
| 已解析且标记规范化的 512 KiB 请求，200 次转换 | 175.717 ms | 0.099 ms |

缓存写入取消了每次 O(n) 的全历史扫描，过期索引的插入/删除为 O(log n)，无过期项时检查堆顶为 O(1)。历史本身的 JSON 序列化仍然存在，过期项的批量清理也仍有成本。规范化请求的转换节省来自跳过整个历史的重复序列化；需要新注入标记或修改系统提示词的请求仍会序列化。这些数据只衡量指定本地 CPU 路径，不代表上游模型速度或整站吞吐量。
